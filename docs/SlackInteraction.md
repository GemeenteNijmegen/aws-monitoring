# Slack interaction: suppress Security Hub findings

Real-time Security Hub alerts in Slack can carry a **Suppress** button. A member of a configured Slack user group
can click it, give a reason, and the finding is set to `SUPPRESSED` in Security Hub with the reason stored as a note.
The daily Security Hub overview does not have buttons.

The feature is off until `securityHubActionsUserGroupId` is set for an environment (see [Setup](#setup-per-environment)).
While it is unset no endpoint is deployed and no button is shown.

## What the button does
- The button appears only on alerts with severity `CRITICAL` (for now). It is one constant in
  `src/monitoringLambda/SecurityHubView.ts` (`SUPPRESS_SEVERITY`).
- For a critical alert the monitoring Lambda looks up the finding with `GetFindings`. The button is shown only when
  exactly one finding matches and its workflow status is `NEW` or `NOTIFIED`. Otherwise (no match, several matches,
  already handled, lookup error) the alert is posted without a button and says "Actions unavailable for this alert".
  An alert is never lost because of the lookup.
- Click: a modal asks for a reason. Submit: the reason is queued and a worker suppresses the finding, then redraws the
  Slack message with the new status, who did it and the reason.

## Setup per environment
Each environment has its own Slack app, API Gateway, signing secret and bot token.

| Environment | Slack app |
|---|---|
| `main` | Monitoring |
| `sandbox` | Sandbox monitoring |

For each environment:

1. In the Slack app settings, under OAuth & Permissions, add the bot scope `usergroups:read`
   (reference: `src/audit/slackbot-manifest.json`).
2. Under Interactivity & Shortcuts, enable Interactivity and set the request URL to the environment's API Gateway
   URL plus `/slack`, for example `https://<api-id>.execute-api.<region>.amazonaws.com/prod/slack`. The API URL
   is shown in the API Gateway console of the `IntegrationsStack` of that environment. The Events URL stays
   `.../slackbot` (audit slackbot).
3. Reinstall the app to the workspace so the new scope takes effect.
4. Store the values in the two Secrets Manager secrets created in `src/audit/AuditSupport.ts`, as plain text:
   - `slackbot-secret-<env>`: the app's Signing Secret (Basic Information).
   - `slack-bot-token-<env>`: the Bot User OAuth Token (starts with `xoxb-`).

   These are the construct IDs; CloudFormation adds a generated suffix to the physical secret name. The dev
   secrets may never have been filled, check them.
5. Put the Slack user group ID (starts with `S`) in `securityHubActionsUserGroupId` for the environment in
   `src/DeploymentEnvironments.ts` and deploy. Setting it without `deployAuditSlackbot` fails synthesis.
   Currently the key is unset in both `main` and `sandbox`, so the feature is off.

Prod and dev both run in the audit account and read the same central findings. A click in the dev app changes real
findings, so keep the dev user group limited to testers.

## Behavior
- **Who can click:** anyone can open the modal; membership of the user group is checked by the worker with
  `usergroups.users.list`. Not a member, or any error in the check, means refused and nothing is changed.
- **Reason:** required, at most 400 characters (the form enforces it, the receiver checks again). The note text is
  `Suppressed via Slack by <user id>: <reason>`, cut to Security Hub's 512 characters.
- **Note replacement:** the note replaces any earlier note on the finding. Earlier text remains only in the finding
  history.
- **Stale clicks:** the worker reads the finding again. If it is not `NEW` or `NOTIFIED` nothing is written; the user
  gets an ephemeral message with the current status and last note, and the Slack message is redrawn. Already
  `SUPPRESSED` is treated as success without a write. If the finding is no longer `CRITICAL`, or cannot be found,
  nothing is changed either.
- **Redraw and `response_url`:** answers and the redraw go through Slack's `response_url`, which is valid for 30
  minutes. After that the suppress still succeeds; only the redraw fails, and that is logged. The worker only
  contacts `hooks.slack.com`.
- The reason is escaped, so `<!channel>` or `<@user>` in it does not notify anyone.
- Suppression can alert again if the landing-zone forwarding rule does not filter on workflow status
  (`BatchUpdateFindings` also emits an event); check this in the end-to-end test.

## Troubleshooting
- **Nothing happens after Submit:** check the logs of the receiver and worker Lambdas. The log group names are
  generated by CloudFormation; open the function in the Lambda console (Monitor tab, View CloudWatch logs). The
  groups are also in the `IntegrationsStack` resources in CloudFormation, with construct IDs `receiver-logs` and
  `worker-logs` under `security-hub-actions`. Requests with a bad signature get 403 and are logged as "authentication failed".
- **DLQ:** the worker handles each message on its own and logs and drops invalid or failing records, so the DLQ only
  fills if the Lambda itself fails (for example a timeout or crash). Messages are retried once more
  (`maxReceiveCount: 2`), then go to the DLQ, where they stay 14 days. The main queue keeps messages for 1 hour.
  There is no DLQ alarm; check the DLQ in the SQS console.
- **How failures show up:** the user gets an ephemeral Slack message ("You are not allowed to suppress findings.",
  "Could not look up the finding. Please try again.", "Suppressing the finding failed. Please try again.", and so
  on). Details (outcome, finding id, Slack user id, reason length; never the reason itself or the raw request) are in
  the worker logs under "Suppress request handled".
- **No button on a critical alert:** the user group ID is not configured, the lookup found zero or several
  findings, or the finding is not `NEW`/`NOTIFIED`.
- **Slack says the request URL did not respond / dispatch_failed:** check the Interactivity URL ends in `/slack`
  and that the signing secret is filled in.

## Cost
All services are pay-per-use, so the idle cost is about zero. Controls that cap the cost (all in
`src/securityHubActions/SecurityHubActions.ts` unless noted):

| Control | Why it saves or caps cost |
|---|---|
| Lookup only for `CRITICAL` alerts; `GetFindings` `MaxResults: 2`, SDK `maxAttempts: 3`, `requestTimeout: 5s` (`SecurityHubFindingLookup.ts`) | Few API calls; the Lambda timeout cannot be billed by a hung call |
| Reuse the two `AuditSupport` secrets, cached per container | No new secrets (about $0.40/secret/month each), fewer `GetSecretValue` calls |
| No DynamoDB, no VPC/NAT, no KMS CMK; queues use `SQS_MANAGED` encryption | No idle or per-key charges |
| Lambdas `arm64`, 256 MB; receiver timeout 5s, worker 30s | Lower GB-second price, bounded runtime |
| Worker `batchSize: 1`, `maxConcurrency: 2`; DLQ `maxReceiveCount: 2` | Caps parallel spend and retry storms, protects Security Hub and Slack rate limits |
| Throttle on `POST /slack` (5 rps, burst 10), set in `IntegrationsStack.ts` | Caps invocation cost from unauthenticated traffic on a public endpoint |
| Log groups `ONE_MONTH` retention, `Logger` at INFO, no raw request logging | Ingestion is the largest cost line |
| Main queue retention 1 hour, DLQ 14 days | A request older than the `response_url` lifetime is not worth storing |
| Resources tagged `Feature=security-hub-actions` | Spend visible per feature |

**Estimate (verify with the AWS Pricing Calculator):** at tens of critical alerts and a few suppressions per month,
the added cost is well under $1/month, dominated by CloudWatch Logs and API Gateway requests. `GetFindings` and
`BatchUpdateFindings` are free.

**Seeing the spend:** the `Feature` tag only shows up in Cost Explorer after it is activated as a cost allocation tag
in the Billing console (Cost allocation tags, user-defined). This needs to be done once, by someone with billing
access in the management account; costs are tagged from activation onwards. Then filter Cost Explorer on
tag `Feature` = `security-hub-actions`.

Not included: a DLQ alarm (about $0.10/month, a later decision) and log retention changes for existing Lambdas.
